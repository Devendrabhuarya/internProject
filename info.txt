
› could you explain matric


• Yes. In your benchmark, metrics are the numbers used to compare RabbitMQ and MQTT.

  Main Metrics

  1. Sent

  Number of messages the publisher tried to send.

  Example:

  sent = 1000

  This means the publisher attempted to send 1000 messages.

  2. Received

  Number of messages the subscriber/consumer actually received.

  Example:

  received = 998

  This means 998 messages reached the receiver.

  3. Lost

  Messages that were sent but not received.

  Formula:

  lost = sent - received

  Example:

  sent = 1000
  received = 998
  lost = 2

  Lower is better.

  4. Success Rate

  Percentage of messages successfully received.

  Formula:

  success rate = received / sent * 100

  Example:

  998 / 1000 * 100 = 99.8%

  Higher is better. Ideally it should be 100%.

  5. Duration

  Total time taken by the subscriber/consumer to receive the messages.

  Example:

  duration_seconds = 2.5

  This means the receiver took 2.5 seconds to receive the messages.

  6. Throughput

  How many messages are processed per second.

  Formula:

  throughput = received / duration_seconds

  Example:

  1000 messages / 2 seconds = 500 messages/second

  Higher throughput means the system can handle more messages quickly.

  7. Latency

  Latency means how long one message takes to travel from publisher to subscriber.

  In your code, latency is measured from:

  message created by publisher

  to:

  message received by subscriber

  Lower latency is better.

  Latency Sub-Metrics

  Minimum latency

  Fastest message delivery time.

  min = 1.2 ms

  Average latency

  Average delivery time of all messages.

  avg = 5.4 ms

  Useful, but can be affected by a few very slow messages.

  Median latency

  Middle value after sorting all latencies.

  median = 4.8 ms

  Often more reliable than average because it is less affected by extreme values.

  P95 latency

  95th percentile latency.

  Example:

  p95 = 12 ms

  This means 95% of messages were delivered within 12 ms, and 5% were slower.

  P95 is very important because it shows worst-case behavior better than average.

  Maximum latency

  Slowest message delivery time.

  max = 25 ms

  Shows the worst single message delay.

  Publisher Rate

  In the automated runner, you may also see:

  publisher_rate_msg_per_sec

  This means how fast the publisher sent messages.

  Formula:

  sent / publisher_duration

  It is different from subscriber throughput.

  Subscriber Throughput vs Publisher Rate

   Metric                   Meaning
  ━━━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Publisher rate           How fast messages were sent
  ───────────────────────  ───────────────────────────────────────────
   Subscriber throughput    How fast messages were received/processed

  If publisher rate is very high but subscriber throughput is low, the broker or consumer may be the
  bottleneck.

  › how publisher and subscriber is running ? and where is broker


• In your project, there are three parts:

  Publisher  ->  Broker  ->  Subscriber/Consumer

  1. Broker

  The broker is RabbitMQ or MQTT server.

  It is running inside the Podman/Docker container.

  For RabbitMQ:

  docker run --rm -p 5672:5672 --name rabbitmq-benchmark rabbitmq:3-management

  Broker location:

  RabbitMQ broker = inside container
  Host access = localhost:5672

  For MQTT:

  docker run --rm -p 1883:1883 --name mqtt-benchmark eclipse-mosquitto:2 mosquitto -c /mosquitto-no-
  auth.conf

  Broker location:

  MQTT broker = inside container
  Host access = localhost:1883

  You can see brokers with:

  podman ps

  2. Publisher

  The publisher is your Python process.

  When you run:

  python benchmark_rabbitmq.py --role publisher --count 1000 --payload-size 256

  or:

  python benchmark_mqtt.py --role publisher --count 1000 --payload-size 256 --qos 1

  that Python script becomes the publisher.

  It sends messages to the broker.

  3. Subscriber / Consumer

  The subscriber is also your Python process, but running in a different role.

  RabbitMQ calls it a consumer:

  python benchmark_rabbitmq.py --role subscriber --count 1000 --payload-size 256

  MQTT calls it a subscriber:

  python benchmark_mqtt.py --role subscriber --count 1000 --payload-size 256 --qos 1

  It receives messages from the broker.

  When using automated runner

  When you run:

  python run_benchmarks.py --systems rabbitmq --runs 5 --counts 1000 --payload-sizes 256

  the runner automatically starts two Python processes:

  Process 1: benchmark_rabbitmq.py --role subscriber
  Process 2: benchmark_rabbitmq.py --role publisher

  The broker is not started by the runner. The broker must already be running in Podman/Docker.

  So the complete RabbitMQ flow is:

  Python subscriber process
          ^
          |
  RabbitMQ broker inside Podman container
          ^
          |
  Python publisher process

  More accurately:

  Publisher Python process
      |
      | sends to localhost:5672
      v
  RabbitMQ broker container
      |
      | delivers from queue
      v
  Subscriber Python process

  For MQTT:

  Publisher Python process
      |
      | publishes to localhost:1883 topic
      v
  Mosquitto broker container
      |
      | forwards topic messages
      v
  Subscriber Python process

  So in short:

   Part                   Where it runs
  ━━━━━━━━━━━━━━━━━━━━━  ━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
   Broker                 Inside Podman/Docker container
  ─────────────────────  ──────────────────────────────────────────────────────────────
   Publisher              Your local Python process
  ─────────────────────  ──────────────────────────────────────────────────────────────
   Subscriber/Consumer    Your local Python process
  ─────────────────────  ──────────────────────────────────────────────────────────────
   Automated runner       Your local Python process that starts publisher + subscriber
